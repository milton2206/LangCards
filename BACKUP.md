# Бэкапы и восстановление

## Что на самом деле входит в Supabase Free

Честно, без иллюзий:

- **Автоматических бэкапов на Free-тарифе НЕТ.** Ежедневные бэкапы начинаются с
  тарифа Pro; они хранятся 7 дней.
- **Point-in-Time Recovery (PITR) — тоже платный** (Pro + отдельная надстройка).
  На Free откатиться «на вчера» нельзя.
- Проекты Free, **неактивные 7 дней, ставятся на паузу**; после долгой паузы
  проект и его данные могут быть удалены. Пауза — не бэкап.

Вывод: единственная страховка на Free — **снимать логический дамп самому**. Для
этого и нужен скрипт ниже. Снимай его **перед каждой миграцией** и обязательно
**до первого нажатия «Удалить аккаунт»**.

## Как сделать бэкап (одна команда)

```bash
npm run backup
```

Скрипт читает `SUPABASE_URL`/`VITE_SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` из
`.env.local`, выгружает все пользовательские данные и кладёт файл в `backups/`:

```
backups/langcards-backup-2026-07-26_14-05-09.json
```

Дата и время — в имени, ручных шагов нет. Что попадает в дамп:

| Раздел            | Что                                                        |
|-------------------|-----------------------------------------------------------|
| `auth_users`      | id + email аккаунтов (пароли Supabase не отдаёт)          |
| `profiles`        | профили                                                    |
| `user_words`      | весь прогресс слов (jsonb)                                 |
| `user_languages`  | языковые пары, приоритеты, лимиты, свои темы              |
| `feedback`        | отзывы пользователей                                       |
| `placement_items` | общий банк заданий теста (не персональный, но восстановим)|

> **Папка `backups/` в `.gitignore`** — в дампе есть email'ы (персональные
> данные), в репозиторий они попадать не должны. Храни дампы в надёжном месте.

Счётчики суточных лимитов (`api_usage`) в дамп не входят намеренно: это
эфемерные данные, обнуляются каждый день, терять нечего.

## Как восстановиться

Сначала — сухой прогон (ничего не пишет, только показывает план):

```bash
npm run restore -- backups/langcards-backup-2026-07-26_14-05-09.json
```

Если план устраивает — применить:

```bash
npm run restore -- backups/langcards-backup-2026-07-26_14-05-09.json --apply
```

Восстановление — это **upsert по первичному ключу**: строки из дампа
возвращаются на место, существующие перезаписываются значениями из дампа.
Операция **аддитивная и идемпотентная — она ничего не удаляет**.

### Главный сценарий страховки (ради него всё и делается)

Ты вот-вот впервые нажмёшь «Удалить аккаунт». Порядок:

1. `npm run backup` — свежий дамп.
2. Удаляешь **тестовый** аккаунт.
3. Проверяешь, что исчез только он, а данные остальных целы.
4. **Если что-то пошло не так** и удаление задело чужие строки — а сами их
   аккаунты в `auth.users` целы — `npm run restore -- <файл> --apply` вернёт
   снесённые строки на место (внешние ключи выполнятся, потому что владелец
   существует).

### Чего восстановление НЕ делает

- **Не воссоздаёт строки в `auth.users`.** Если удалён сам аккаунт (а не только
  его данные), вставить его строки-потомки нельзя — не даст внешний ключ. В
  дампе есть `auth_users` (id + email), по ним аккаунт при необходимости
  пересоздают вручную через Admin API. Но обычная страховка от «удаление задело
  лишнее» этого не требует: удаляется всегда ровно один аккаунт, а страдают (в
  худшем случае) данные других, чьи аккаунты живы.
- **Ничего не удаляет.** Строки, появившиеся уже после снятия дампа, останутся.
